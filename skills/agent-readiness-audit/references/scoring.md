# Scoring

Ten principles, 0–10 each, **unweighted sum** = headline out of 100.

| Band | Range | Meaning |
|---|---|---|
| Strong | 8–10 | Encoded into a check, or structurally impossible to violate |
| Adequate | 6–7 | Right idea, documented but unenforced, or done in one tier only |
| Weak | 0–5 | Absent, or actively working against the agent |

## Discipline

**Score on enforcement, not intent.** The dividing line between 7 and 8 is almost always
"is this checked by a machine?" A documented architecture that nothing verifies is a 7 at
best, however good the architecture is. This is the rubric's core bias and it should show
in the scores.

**Composite, not best-of.** In a monorepo, score the repo as a whole. Backend at 10 and
frontend at 2 is a **6**, and the one-line verdict must name the divergence: "Backend
exemplary; frontend is role-first and fans a feature across seven directories."

**Every score needs a count, a path, or a quote.** If you can't attach evidence, you
haven't finished step 2. Impressions are not scores.

**Use the full range.** A rubric returning 8s everywhere is not measuring anything.
Most healthy production repos land 55–75. Above 85 is rare and requires enforcement on
nearly every principle. Below 40 means the agent is mostly guessing.

**Small-repo leniency.** Under ~100 source files and a single stack, P1, P2, and P5 are
largely inapplicable — a flat layered layout is genuinely correct at that size. Score
them at 7 by default rather than penalizing, and say so explicitly in the report.

## Per-principle anchors

### P1 — Organize around behavior
- **10** Feature-first throughout; layers inside features; shared kernel with a stated direction
- **8** Feature-first in the main source tree; a few role directories survive at the edges
- **6** Feature grouping applied one level too deep, or one tier feature-first and another role-first
- **4** Role-first throughout; a typical feature spans 4+ top-level directories
- **2** Role-first *and* deep — a change requires opening six directories to read one behavior

### P2 — Explicit, enforced dependency direction
- **10** Boundaries asserted by tests or lint across every tier, including a vendor-SDK ban on the innermost layer; no cycles
- **8** Enforced in the primary tier, documented in the others
- **6** Direction clearly documented and mostly honored; nothing checks it
- **4** Implicit direction, discoverable only by reading imports
- **2** Cycles, global mutable state, or business rules interleaved with I/O

### P3 — Names own the concept
- **10** No dumping grounds; naming convention machine-enforced; file path derivable from the concept
- **8** Precise, consistent names; a couple of ambiguous spots
- **7** Precise but not *predictable* — e.g. two same-role buckets, or a stale name across the source
- **5** Several generic files accumulating unrelated code
- **3** `utils.ts` / `helpers.ts` / `manager.ts` as primary organizing units

### P4 — One canonical workflow
- **10** One root entry point, fast + full tiers, CI invokes the same script, auto-run on edit or commit
- **8** Root entry point and CI parity; missing a fast tier or auto-invocation
- **7** Good verifier but **no root entry point**, or **CI restates the steps** instead of invoking it *(cap here for either)*
- **5** Commands exist but differ between README, CI, and practice
- **2** No single verification command; agent must assemble one

### P5 — Instructions close to the code
- **10** Lean root core with on-demand routing, plus module-local instruction files; invariants encoded where possible
- **8** Excellent root layer; nothing colocated with the modules it governs
- **6** One instruction file, moderately long, broadly accurate
- **4** A long wiki-style doc, partly stale
- **2** No instructions, or instructions that contradict CI

### P6 — Tests mirror behavior
- **10** Test path derivable from source path; single-test execution obvious; tests independent
- **8** Mirrored layout; single-test execution requires a documented but non-obvious flag
- **6** One tier mirrored, another flat; or mirrored but a full run is needed for any change
- **4** Flat test directory with no path relationship to source
- **2** Flat, misleadingly named, no single-test execution, inconsistent naming

### P7 — Generated and external code separated
- **10** Gitignored and regenerated by verify, header-marked, tool-excluded, drift-gated
- **9** All of the above but committed, or missing `linguist-generated`
- **7** Separate directory plus headers; not excluded from tooling
- **5** Separate directory only
- **2** Generated or vendored files interleaved with hand-written source, or vendored code with local edits

### P8 — One live implementation per concept
- **10** No versioned/legacy names; dead-code detection runs in verify
- **8** Clean, with a misleading name or two; dead-code tool exists but is manual
- **6** One or two dormant parallel implementations, clearly marked
- **4** Live `v1`/`v2` pairs where reachability isn't obvious from the filename
- **2** Multiple parallel implementations, some tested, none marked

### P9 — Consistency over local optimality
- **10** One way to do each thing, enforced; migrations finished
- **8** Uniform in practice; enforced in the primary tier only
- **7** Two or three unfinished migrations with no stated target convention
- **5** Several competing patterns of similar vintage
- **3** Every module a different style; pattern-matching from neighbors is unreliable

### P10 — Right-sized files
- **10** Nothing over ~800 lines; a `max-lines` rule prevents regression
- **8** A handful over 800, none over 1,400, distribution otherwise healthy
- **7** Several over 800 and one or two over 1,400, some on hot paths; no rule preventing growth
- **5** Many over 1,000, including core modules
- **3** Multi-thousand-line files on the primary change paths

## Ordering the remediation list

Rank by **payoff per hour**, not by score. The ordering that usually holds:

1. Make CI invoke the canonical verifier *(hours — makes every later fix self-enforcing)*
2. Enable single-test execution *(hours — largest feedback-loop gain available)*
3. Add a root entry point *(hours — usually just exposing logic that already exists)*
4. Restructure tests to mirror source *(a day — mechanical)*
5. Merge duplicate helper buckets *(hours — removes a coin flip from every future file)*
6. Add module-local instruction files *(hours)*
7. Port boundary enforcement to unenforced tiers *(a day — architecture already exists)*
8. Rename misleading files; add dead-code detection to verify *(an hour)*
9. Add a `max-lines` rule with an allowlist *(hours — stops growth without fixing today)*
10. Restructure to feature-first *(weeks — **defer**; a half-done version is worse than not starting)*

Adjust to what the evidence actually found, but keep the shape: cheap structural fixes
that make other fixes stick come first; the one genuine project goes last with an
explicit warning about partial migration.
